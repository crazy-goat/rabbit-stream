# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added
- **`Exception\LengthException`** — a value too long to be represented on the wire. Extends `\LengthException` (BC) and implements `RabbitStreamExceptionInterface` (#394).
- **A regression test enforcing the #242 hierarchy** — `tests/Exception/ExceptionHierarchyTest.php` scans every file under `src/` for `throw new \Something(...)` and fails on any hit, asserts every class in `src/Exception/` implements `RabbitStreamExceptionInterface`, and locks in that `InvalidArgumentException`/`LengthException` still extend their native namesakes. `src/` is now free of native throwables, so the guarantee is testable rather than aspirational (#394).
- **Enhancement: the AMQP recursion depth limit is configurable from the consumer (#450)** — #397 made `maxDepth` a parameter of `AmqpDecoder::decodeValue()`/`decodeMessage()`, but nothing on the exposure path passed it, so operators were stuck with the default of 32. `Connection::createConsumer()` and `createSuperStreamConsumer()` now take `int $maxDecodeDepth = AmqpDecoder::MAX_RECURSION_DEPTH` (validated `>= 1`), threaded through `Consumer` → `OsirisChunkParser::parseMessages()` → `Message`, and `AmqpMessageDecoder::decode()`/`decodeAll()` take a `maxDepth` too. Because decoding is **lazy**, the limit is stored on each `Message` and enforced by the accessor that triggers the decode (`getBody()`, `getApplicationProperties()`, ...), not by `read()` — the issue's suggestion of a `read()` parameter would not have worked. `AmqpDecoder::MAX_RECURSION_DEPTH` is now public so callers can name the default.
- **Enhancement: `decodeMessage()` now says what a non-AMQP payload probably is (#456)** — the exception for a payload that does not start with the described-type marker named only the byte mismatch. It now adds that this is what a raw, un-framed body looks like (e.g. an entry published by rabbit-stream before #413 and still sitting in the stream) and that such entries have to be read as raw bytes via `OsirisChunkParser::parseEntries()` and `ChunkEntry::getData()`.
- **Feature: recovery after `MetadataUpdate` — publishers re-declare, subscriptions re-subscribe, super-stream partitions refresh (#499)** — the broker pushes `MetadataUpdate` (`0x0010`) when a stream becomes unavailable (deleted, or its leader moved) and drops every publisher and subscription declared on it; the client only forwarded the frame to the global `onMetadataUpdate()` callback, so a `Producer` kept publishing into a void and a `Consumer` silently stopped receiving. `StreamConnection` now dispatches the frame per stream first, via `registerMetadataUpdateHandler(string $stream, string $handlerId, callable $handler)` / `unregisterMetadataUpdateHandler(string $stream, string $handlerId)`, and only then to the global callback (which is unchanged), and logs every `MetadataUpdate` at warning level. `Producer` registers a handler for its own stream and marks itself **stale**; the next `send()`/`sendBatch()`/`sendWithFilter()` re-runs `DeclarePublisher` before publishing, retrying with exponential back-off (50 ms → 1 s) for up to the new `redeclareTimeout` (default 5.0 s, `Producer::DEFAULT_REDECLARE_TIMEOUT`, also exposed on `Connection::createProducer()`/`createSuperStreamProducer()`) while the stream is `STREAM_NOT_EXIST`/`STREAM_NOT_AVAILABLE`, and throwing a `ProtocolException` carrying the broker's response code when it is still gone; a named producer re-reads its publishing sequence on re-declare so publishing IDs never collide. Messages that were unconfirmed when the stream went away can never be confirmed, so they are reported to `onConfirm` as failed `ConfirmationStatus` objects with the `MetadataUpdate` response code and stop counting toward `maxPendingConfirms` (previously `waitForConfirms()` would block until its timeout for messages that no longer existed). A `PublishError` with `PUBLISHER_NOT_EXIST` or `STREAM_NOT_AVAILABLE` triggers the same path, covering a missed `MetadataUpdate`. `Consumer` marks the subscription lost, drops its now-meaningless in-flight credit, and re-`Subscribe`s from `read()`/`readOne()` with the same back-off; the resume position is chosen from `StreamStats` — right after the last processed message when the stream was merely unavailable, or the consumer's initial `OffsetSpec` when the committed offset shows the stream was recreated from scratch (resuming at the old offset would otherwise wait forever) — and the adaptive credit window from #500 is granted again so throughput returns to where it was. `SuperStreamProducer` re-resolves its partition list on the next publish after a `MetadataUpdate` on any partition, closing and dropping the producers of partitions that no longer exist and calling the new `RoutingStrategy::reset()` (implemented by `HashRoutingStrategy` as a no-op and by `KeyRoutingStrategy` as a route-cache flush), which removes the "partition membership is resolved once" caveat documented in #494/#497; RabbitMQ cannot add partitions to an existing super stream, so a refresh only ever shrinks the routing set. New introspection: `Producer::isStale()`/`getRedeclareCount()`, `Consumer::isSubscriptionLost()`/`getResubscribeCount()`/`resubscribeIfLost()`, `SuperStreamProducer::isPartitionsStale()`/`refreshPartitions()`/`getRefreshCount()`. `Producer::close()` and `Consumer::close()` unregister their handler and skip `DeletePublisher`/`Unsubscribe` when the broker already dropped them. Verified end to end against RabbitMQ 4.3.5 (`tests/E2E/MetadataUpdateRecoveryE2ETest.php`: delete-and-recreate a stream under an active producer and consumer, delete one partition under an active `SuperStreamProducer`). Docs: `guide/publishing.md` §6, `guide/consuming.md` §9, `guide/super-streams.md`, `api-reference/{producer,consumer,super-stream-producer,stream-connection,connection}.md`
- **Feature: adaptive credit window in bytes (#500)** — `Consumer` (and `Connection::createConsumer()` / `createSuperStreamConsumer()`) gained `creditWindowBytes` (default 8 MiB). Credit is chunk-granular on the wire and chunk size depends on how the producer published (thousands of messages per chunk on a batched plain stream, a handful on a super-stream partition fed one message at a time), so a fixed `initialCredit: 10` collapsed to ~50 messages per round trip over a network (measured 8–45k msg/s). The consumer now tracks the observed chunk size and keeps `ceil(creditWindowBytes / avgChunk)` chunks in flight, never below `initialCredit` and never above `Consumer::MAX_CREDIT` (32,767); `0` disables the adaptation. `Consumer::getCreditTarget()` exposes the current target. `initialCredit` is now validated to 1–32767
- **Bug: a Credit frame with a value of 32,768 or more silently stopped the subscription** — the protocol documents the field as uint16, but RabbitMQ (verified on 4.3.5) decodes it as a signed 16-bit integer, so the subscription's credit went negative and no Deliver ever followed, with no error frame. `Consumer` now caps every Credit request and its in-flight target at `Consumer::MAX_CREDIT` = 32,767 (the previous cap was 65,535)
- **Docs: super-stream throughput over a network (#501)** — `advanced/performance-tuning.md` gained a section with the Hetzner measurements (batch publishing vs per-message `send()`, chunk size, credit window, what scaling consumers across machines buys), `guide/flow-control.md` explains chunk-granular credit and the byte window, `guide/super-streams.md` links to both
- **Bug: `Consumer::read()`/`readOne()` returned early when a non-Deliver frame arrived first** — a heartbeat, a publish confirm from a producer on the same connection or a single-active-consumer `ConsumerUpdate` counted as the one frame of `readLoop(maxFrames: 1)`, so `read($timeout)` came back empty long before `$timeout` and callers mistook it for an idle stream. Both methods (and `SuperStreamConsumer`'s) now keep waiting until a message is buffered or the deadline passes. `StreamConnection::readLoop()`/`Connection::readLoop()` return the number of dispatched frames (`int` instead of `void`; 0 = timeout, `stop()` or disconnect) so the wait can stop as soon as the loop reports nothing to wait for
- **Bug: `StreamConnection::request()` returned an unsolicited `CreditResponseV1` as the reply** — the broker sends a Credit response only on error (e.g. credit for a subscription that just lost a single-active-consumer election) and it carries no correlation ID; when it arrived while a correlated `request()` was waiting (surfaced as `Expected QueryOffsetResponseV1, got CreditResponseV1` with several SAC consumers on a super stream) it was handed to the caller. Responses without a correlation ID are now logged at warning level and skipped by `request()`; plain `readMessage()` still returns them
- **Feature: `SuperStreamProducer` and routing strategies (#494)** — `Connection::createSuperStreamProducer(string $superStream, ?RoutingStrategy $strategy = null, ?string $name = null, ?callable $onConfirm = null, int $maxPendingConfirms = Producer::DEFAULT_MAX_PENDING_CONFIRMS): SuperStreamProducerInterface` resolves the super stream's partitions (via `Connection::partitions()`) and returns a `SuperStreamProducer` that routes each `send()`/`sendBatch()` call to the correct partition(s) via a pluggable `CrazyGoat\RabbitStream\Client\Routing\RoutingStrategy`, opening a `Producer` per partition **lazily** on first publish to it. Two strategies ship: `HashRoutingStrategy` (the default) hashes the routing key with a new pure-PHP `Murmur3::hash32()` (MurmurHash3 x86_32, seed `104729` — `HashRoutingStrategy::SEED`) and takes the unsigned result modulo the partition count, matching the Java and .NET RabbitMQ Stream clients exactly so a routing key lands on the same partition regardless of the publishing client's language; `KeyRoutingStrategy` instead calls the existing broker-side `Connection::route()` once per distinct routing key and caches the result in memory, throwing the new `NoRouteForKeyException` (extends `RabbitStreamException`) when the broker has no binding for a key. Named producers get per-partition publisher names `"{$name}-{$partition}"` so per-partition sequence dedup (`Producer::querySequence()`) still works. `sendBatch()` takes `list<array{0: string, 1: string}>` `[message, routingKey]` pairs, grouped per destination partition before one batch send per partition. Caveat documented on `SuperStreamProducer`: partition membership is resolved once at construction — a topology change (partition leader change, or the super stream's partition set itself changing) is not automatically detected; recreate the producer to pick it up
- **Feature: `SuperStreamConsumer` and `Message::getStream()` (#495)** — `Connection::createSuperStreamConsumer(string $superStream, OffsetSpec $offset, ?string $name = null, int $autoCommit = 0, int $initialCredit = 10, bool $singleActiveConsumer = false): SuperStreamConsumerInterface` resolves the super stream's partitions and subscribes a plain `Consumer` to every one of them, all sharing the same `$name` (required for the broker to group them into one single-active-consumer group per partition). `SuperStreamConsumer::read()` drains any already-buffered messages across all partitions without blocking if anything is buffered, otherwise performs exactly one bounded `readLoop()` pass and then collects; `readOne()` round-robins fairly across partitions with buffered data so one high-traffic partition can't starve the others. `storeOffset(string $partition, int $offset)`/`queryOffset(string $partition): int` make offset tracking explicitly per-partition — there is no aggregate, super-stream-wide offset. `Message` gained `getStream(): ?string`, set once at construction from the subscribing `Consumer`'s stream name (null when constructed outside a `Consumer`'s deliver path), which is how a caller tells partitions apart in `SuperStreamConsumer`'s aggregated `read()`/`readOne()` results. `Consumer` gained `hasUnread(): bool` and `drain(): array` (both no-I/O, buffer-only operations) to support this aggregation.
- **Docs: the high-level super-stream API documented (#434, closes #330/#175)** — `Connection::createSuperStream()`, `deleteSuperStream()` and `route()` were added on 2026-05-21 (`e2eb878`, #330/#175) two months after `docs/en/` was frozen (`f10a0d5`, 2026-03-29), so the convenient, supported API was invisible to users; `guide/super-streams.md` and `examples/super-stream-routing.md` still taught the raw-request path exclusively. Both are rewritten around the real high-level API — `createSuperStream`/`deleteSuperStream` (unchanged, verified still accurate), `Connection::partitions()`, `Connection::route()`, `SuperStreamProducer` with both routing strategies (Murmur3 seed `104729` called out explicitly for Java/.NET cross-client compatibility), `SuperStreamConsumer`, single active consumer on super streams, per-partition offset tracking, and the `SuperStreamConsumer::close()` known limitation above — and two runnable scripts were added, `examples/super_stream_producer.php`/`examples/super_stream_consumer.php`. `api-reference/connection.md` gained `partitions()`, `createSuperStream()`, `deleteSuperStream()`, `route()`, `createSuperStreamProducer()` and `createSuperStreamConsumer()`; two new pages, `api-reference/super-stream-producer.md` and `api-reference/super-stream-consumer.md`, were added and registered in `docs/index.md`. Also documents `Producer::sendWithFilter()` in `api-reference/producer.md` and `Message::getStream()` in `api-reference/message.md`, both left undocumented by earlier work (#380/#495)
- **Feature: `Subscribe` Properties map — stream filtering, single active consumer, super streams (#380)** — `SubscribeRequestV1` now serializes a trailing `Properties` map (count + key/value strings), previously always omitted so the broker-side features gated behind it (filtering, single active consumer, super-stream partitioning) were unreachable. An empty map still produces byte-identical output to before. `Connection::createConsumer()`/`Consumer` gained typed parameters: `filterValues` (list of stream filtering values, sent as `filter.0`, `filter.1`, ... properties), `matchUnfiltered` (also deliver messages published with no filter value), `singleActiveConsumer` (requires `name`, throws `InvalidArgumentException` otherwise), and `superStream`. `Producer::sendWithFilter(string $message, ?string $filterValue)` publishes via the existing `PublishRequestV2`/`PublishedMessageV2` with a filter value. Stream filtering is broker-side and **chunk-granular** (a bloom filter per chunk): a chunk is delivered once its filter may contain a matching value, and every message in a delivered chunk arrives, matching or not — exact filtering needs application-side post-filtering. Docs: `docs/en/guide/consuming.md` §7–8, `docs/en/api-reference/consumer.md`, `docs/en/api-reference/connection.md`
- **Feature: high-level single active consumer support (#496)** — `StreamConnection` now dispatches `ConsumerUpdate` per subscription via `registerConsumerUpdateHandler()`/`unregisterConsumerUpdateHandler()` (dropped automatically by `unregisterSubscriber()`), falling back to the existing global `onConsumerUpdate()` callback, then to "none" (#460). A `Consumer` created with `singleActiveConsumer: true` registers a handler automatically: on activation it resumes from `queryOffset() + 1` (or its initial `OffsetSpec` if nothing is stored, tolerating the broker's "no offset" response), and on deactivation it stores its last processed offset (when `autoCommit` is enabled) so the next active consumer resumes without gaps. `Consumer::onConsumerUpdate(callable(bool $active, Consumer $consumer): ?OffsetSpec)` overrides this logic; `Consumer::isActive()` exposes the current activation state (added to `ConsumerInterface`). `StreamConnection::request(object $request, float $timeout = 30.0): object` sends a correlated request and returns the reply matched by correlation ID, parking replies that belong to other in-flight requests (handed to their `request()` or to the next `readMessage()`); `Consumer` uses it for Subscribe, QueryOffset and Unsubscribe, so the handler's nested `queryOffset()` round-trip cannot steal an outer request's response even when the broker pushes ConsumerUpdate before the SubscribeResponse

### Fixed
- **Bug: `KeyEnum::fromStreamCode()` threw a bare `\ValueError`, escaping the exception hierarchy (#394)** — it is reached from `ResponseBuilder::fromResponseBuffer()` for **every** inbound frame, so a single junk 2-byte key, or a command added by a future RabbitMQ, escaped an application's `catch (RabbitStreamExceptionInterface)` consume loop as an unhandled error and took the worker down. It now throws `ProtocolException` with the same `Unknown stream protocol command code: 0x%04x` message; `getResponseCode()` is `null`, because the frame was never decoded far enough to have one. Callers catching `\ValueError` there must switch to `ProtocolException` (or the interface).
- **Bug: `Connection::create()` threw the global `\InvalidArgumentException` (#465)** — the library's main entry point validated `requestedFrameMax`, `requestedHeartbeat`, `maxDeliverFrameSize` and `socketTimeout` with the native class (four sites; the issue reported two), so the one `catch (RabbitStreamExceptionInterface)` the #242 hierarchy exists for missed all of them. Now throws `CrazyGoat\RabbitStream\Exception\InvalidArgumentException`. Not a BC break — that class extends the native one, so existing `catch (\InvalidArgumentException)` code keeps working.
- **Bug: `PublishErrorResponseV1::fromStreamBuffer()` threw a bare `\Exception` (#466)** — the last generic `\Exception` anywhere in `src/` after #242. The guard is unreachable today (`PublishingError::fromStreamBuffer()` always returns an instance), but the interface permits `null`, so instead of deleting the guard it now throws `DeserializationException` naming which error of how many failed, for which publisher, and at what buffer offset — a future graceful-`null` there cannot reintroduce a hierarchy-escaping throw.
- **Bug: `AmqpMessageEncoder::encodeDataSection()` threw a bare `\LengthException` (#394 audit)** — not reported in any issue, found by auditing `src/` for native throwables as #394 asks. The over-4 GiB payload guard added in #413 escaped the hierarchy the same way. New `CrazyGoat\RabbitStream\Exception\LengthException` extends the native `\LengthException` **and** implements `RabbitStreamExceptionInterface`, so it is now catchable both ways.
- **Bug: the compound readers' content window was one byte too wide (#488)** — `readList8`, `readList32`, `readMap8` and `readMap32` computed `$endPosition = $position + $size - $countWidth` and treated it as an *inclusive* bound, but `size` covers the count field plus the content, so that lands one byte past the last content byte. Every compound therefore decoded in a window one byte too generous, and the #449 available-bytes cap derived from it (`$endPosition - $position + 1`) was one byte looser than the real content length — a frame declaring a `size` one byte short of its actual content was accepted. The window is now exclusive (`$contentEnd`, the first byte after the content), the per-element guards compare with `>=`, and `available` is exactly `$contentEnd - $position`. Two new checks come with it: a `size` smaller than the count field it is defined to include, and a declared content length larger than what remains in the frame, are both rejected up front with a precise message instead of surfacing later as whichever element read happened to run off the end of the string. **The #449 exception messages changed by one byte** (`List32 count 5 exceeds available bytes 3`, previously `4`).
- **Bug: compound types never verified that their elements consumed the declared `size` (#453)** — the four compound readers checked the cursor *before* each element but never after the loop, so a lying `size` was silently accepted: the last element could read past the declared window (individual reads are bounded only by `strlen($data)`), and a `size` larger than the elements present left the cursor short of the compound's end, desynchronising everything decoded after it. Consumption is now asserted to be exact, with `List8/List32/Map8/Map32 size mismatch: declared N bytes, elements consumed M`. Note that this rejects payloads that previously decoded — **the test fixtures and the documented byte examples themselves carried spec-wrong sizes** (several counted the format code and the size byte as part of `size`, or forgot the count byte) and were corrected in the same pass, along with the "Complete Message Example" in the AMQP decoding guide, whose annotated lengths, field positions and `size` values now match bytes that actually decode.
- **Bug: `readMap8`/`readMap32` truncated an odd element count instead of rejecting it (#489)** — an AMQP map's `count` is the total number of keys *and* values, so it must be even; `$numPairs = (int)($count / 2)` quietly rounded an odd (malformed) count down and dropped the orphan key, accepting the frame. An odd count is now rejected with `Map8/Map32 count must be even (keys and values are counted separately), got N`.
- **Bug: a non-binary Data section was silently discarded, handing the caller an empty body (#452)** — `decodeMessage()`'s `case 0x75` only assigned the body `if (is_string($value))`, so a Data section carrying a list, map or described type (which AMQP mid-tier producers do emit) left `body = ''` with no exception and no way for the consumer to notice the loss. AMQP 1.0 defines Data as binary, so anything else is now rejected with `Data section (0x75) must carry binary data, got array`.
- **Bug: `readBinary32`/`readString32`/`readSymbol32` bounds checks could overflow on 32-bit PHP (#451)** — written as `if ($position + $length > strlen($data))`, the addition of an attacker-supplied 32-bit `$length` near `PHP_INT_MAX` wraps negative on a 32-bit build and skips the check entirely, allowing an out-of-bounds `substr()`. All three are now written as subtractions (`$length > strlen($data) - $position`, which cannot overflow since `$position <= strlen($data)`) and additionally reject a negative length.
- **Bug: `ReadBuffer`'s scalar reads returned floats on 32-bit PHP, breaking their `int` types (#458)** — `getUint32()`, `getUint64()` and `getInt64()` use `unpack('N')`/`unpack('J')`, which return a `float` above `PHP_INT_MAX` on a 32-bit build, losing precision on exactly the values that must stay exact (offsets), and `getInt64()`'s sign correction compares against a literal that itself overflows a 32-bit int. Making uint64 work there would need string-based big-integer math, which is disproportionate for a platform that is vanishingly rare on PHP 8.1+, so the library now refuses to run on it instead of returning quietly wrong offsets: `Platform::assertSixtyFourBitIntegers()` throws the new `UnsupportedPlatformException` (a `RabbitStreamException`, so `catch (RabbitStreamExceptionInterface)` covers it) from `ReadBuffer::__construct()` and from the `AmqpDecoder` entry points. `PHP_INT_SIZE` is a compile-time constant, so the check costs one comparison. The 64-bit requirement is now stated in the README and in Requirements.
- **Security: no receive or send timeout was ever set — a stalled peer hung the client forever and every documented timeout was silently infinite (#402)** — neither `SO_RCVTIMEO`, `SO_SNDTIMEO` nor `socket_set_nonblock()` was used anywhere in `src/`. `socket_select()` only proves that *one* byte is readable; `readBytes()` then looped on a blocking `socket_recv(MSG_WAITALL)` until it had all of them, so a peer that sent a 4-byte length prefix and stopped writing blocked `readFrame()` (and with it `Consumer::read($timeout)`, `readMessage($timeout)`, `readLoop(timeout:)`) indefinitely — one misbehaving or malicious peer hung the worker permanently, with no exception and no way for the application to recover, and the `SOCKET_ETIMEDOUT` branch in `readBytes()` was dead code. `StreamConnection::connect()` now sets `SO_RCVTIMEO` and `SO_SNDTIMEO` from the new `$socketTimeout` constructor parameter (`StreamConnection::DEFAULT_SOCKET_TIMEOUT` = 30.0 s, must be > 0, also exposed as `Connection::create(socketTimeout:)` and changeable at runtime with `setSocketTimeout()`/`getSocketTimeout()`), and throws `ConnectionException` when the option cannot be set — a connection whose reads are unbounded must not be reported as usable. This bounds a single socket call, not an operation: the per-call timeouts stay the ones the caller passes
- **Bug: `readBytes()` discarded already-consumed bytes on a receive timeout, permanently desynchronising framing (#390)** — it returned `null` after having consumed part of the requested bytes, `readFrame()` returned `null` too, and those bytes were simply gone: the caller retried and read mid-frame payload as the next 4-byte frame size, typically a bogus multi-gigabyte length that tripped the frame-size guard and killed the connection — or, worse, a plausible one, after which the client silently parsed garbage. A timeout with nothing consumed still returns `null` (the socket is at a frame boundary, so retrying is safe), but a timeout that leaves a frame half-read now closes the connection and throws `ConnectionException` naming the byte counts: the consumed bytes cannot be pushed back, so the byte stream can never be resynchronised. Every read after the length prefix in `readFrameNoWait()` is marked as mid-frame accordingly. Reachability of this path grew with #402, which is what makes the receive timeout fire at all
- **Bug: `socket_write()`'s return value was ignored, so a short write silently truncated the frame (#389)** — `sendFrame()` called `socket_write()` once and never looped on the number of bytes actually written. Under `SO_SNDBUF` pressure, on a large batch `Publish` frame, or when a blocking write is interrupted, the remaining bytes were never sent: the broker read the next frame starting mid-payload, interpreted arbitrary payload bytes as a 4-byte frame length, and either died with a protocol error or waited for gigabytes that never arrived — while the producer believed the message was sent. The frame is now written in a loop until every byte is on the wire (`sendFrame()` always returns `strlen($frame)` on success). A write that cannot even start throws `TimeoutException` (nothing left the client, so the caller may retry the frame); one that leaves a partial frame on the wire closes the connection and throws `ConnectionException`, because the broker cannot resynchronise mid-frame
- **Bug: publisher/subscription ids were uint8 but unbounded and never reclaimed — a long-lived worker died on its 257th producer and leaked every one before it (#388)** — `Connection::createProducer()`/`createConsumer()` handed out ids from ever-incrementing counters while `DeclarePublisher`/`Subscribe` encode them as a uint8, and `$producers`/`$consumers` were never `unset()`, so a worker creating and closing one producer per work unit threw `InvalidArgumentException: Value 256 is out of range for uint8` on the 257th call (with at most one producer alive) and leaked a `Producer` plus its callbacks each time. Ids are now allocated from the live-object map itself — which cannot drift out of sync with it — walking forward from a cursor and wrapping, so a freed id is only reused after the whole range has been handed out once (a late `PublishConfirm`/`Deliver` for a closed publisher/subscription therefore cannot land on a fresh one sharing its id). `Producer::close()`/`Consumer::close()` are now idempotent (`isClosed()`), release their id even when `DeletePublisher`/`Unsubscribe` fails, and drop the connection's reference to the object; 256 *simultaneous* producers or consumers is now a clear `ConnectionException` (`Connection::MAX_CONCURRENT_PUBLISHERS` / `MAX_CONCURRENT_SUBSCRIPTIONS`) instead of an out-of-range uint8
- **Bug: `isConnected()` relied on the sticky `socket_last_error()` and could permanently kill a healthy connection (#391)** — `socket_clear_error()` was never called anywhere in `src/`, and the per-socket error code is sticky: once any non-fatal error had been recorded (a transient `EAGAIN`/`EWOULDBLOCK`/`EINTR`, or now a receive timeout), every later `isConnected()` returned `false` **and force-set** `$connected = false`, aborting an otherwise healthy connection with no underlying cause. The code is now cleared right after it is read, and transient codes are no longer treated as a disconnect
- **Bug: auto-commit stored the last consumed offset instead of `lastOffset + 1`, redelivering that message on every resume (#396)** — `OffsetSpec::offset()` is inclusive, so a consumer that processed offset 100 and restarted was handed message 100 again — a duplicate side effect on every restart for a non-idempotent handler. Auto-commit (every N messages, on `close()`, and on single-active-consumer deactivation) now stores the **next** offset to consume, matching the Java, Go and .NET clients, so stored offsets are portable across clients and go straight into `OffsetSpec::offset()` with no arithmetic; the single-active-consumer activation reply uses the stored value as is instead of adding 1. **Behaviour change:** offsets written by an older version are one too low — resume those consumers once with `OffsetSpec::offset($stored + 1)`, or accept a single duplicate. `Consumer::storeOffset()` itself is unchanged (it stores exactly the value given) but now documents the convention, as do the offset-tracking guide, the consuming guide and the API reference
- **Bug: `Producer::send()` incremented `pendingConfirms` before the write, permanently breaking the counter on failure (#395)** — one `send()` that threw (timeout, connection error, short write) left `pendingConfirms >= 1` forever, so every later `waitForConfirms()` blocked for its full timeout and then threw `TimeoutException` even though all subsequent messages were confirmed, leaving the producer unusable for confirm tracking short of recreating it. `send()`, `sendWithFilter()` and `sendBatch()` now advance both `pendingConfirms` and the publishing id only after the frame has actually been written, so a failed publish consumes no publishing id and leaves nothing pending
- **Bug: `ConsumerUpdate` default reply repositioned the consumer to FIRST, causing full-history replay on every single-active-consumer/super-stream rebalance (#460)** — `StreamConnection::handleConsumerUpdate()` defaulted to `offsetType = 1` (FIRST) whenever no `onConsumerUpdate` callback was registered (which the high-level `Consumer` never did), so every rebalance handover replayed the whole stream from offset 0. The default is now `offsetType = 0` (none — keep current position), matching the Java reference client. The reply's offset type (whether from a callback or a per-subscription handler, see #496) is now validated to be `0`-`5`, throwing `InvalidArgumentException` otherwise. `OffsetSpec` gained `TYPE_NONE`/`OffsetSpec::none()` to represent this value
- **Security: `AmqpDecoder` unbounded element count in `readList32`/`readMap32` — ~576 MB array from one 8 MB message** — the attacker-supplied 32-bit `<count>` field was used directly as the loop bound, so a single ~8 MB frame (within `DEFAULT_MAX_FRAME_SIZE`) carrying a flat list of 8 M null elements built an ~8 M-entry PHP array (~128–256 MB), triggering an uncatchable `Allowed memory size exhausted` fatal at `memory_limit=128M`. This is a **breadth** amplification vector, distinct from the **depth** vector fixed in #397 (a flat list is depth 1, so the recursion guard does not apply). `readList32` and `readMap32` now apply two pre-loop guards: (1) a count-vs-available-bytes cap (the issue's primary suggestion — rejects a `count` larger than the compound's own `size` declares, before any allocation), and (2) a per-compound element ceiling `MAX_COMPOUND_ELEMENTS = 131072` (the "total-element budget" alternative the issue mentions — closes the *honest* large-frame case where `count` truthfully equals the available bytes). Both throw a catchable `DeserializationException` before the allocation loop; the 8-bit readers (`readList8`/`readMap8`) are unaffected (count capped at 255). 11 unit tests cover both vectors, boundary-at-cap, and regression (#449)
- **Performance: `Message` holds a zero-copy VIEW into the chunk instead of a `substr()` copy of its payload** — `OsirisChunkParser::parseMessages()` used to `substr()` each entry's bytes out of the chunk before handing them to `Message::fromRawEntry()`, so a chunk of N lazily-decoded messages cost one chunk buffer *plus* N payload copies. `Message` gained `Message::fromChunkView(int $offset, int $timestamp, string $chunk, int $start, int $length): self`, which stores the chunk string, start and length instead of copying out a substring; PHP strings are refcounted, so every `Message` built from the same chunk just bumps that one buffer's refcount. `ensureDecoded()`'s fast path (single AMQP 1.0 Data section, vbin32/vbin8) now reads the prefix and length field directly out of the chunk at the entry's absolute offset and does exactly one `substr()` to extract the body itself; the generic fallback `substr()`s only the entry's own range before calling `AmqpDecoder::decodeMessage()`. `OsirisChunkParser::parseMessages()` now yields `fromChunkView()` views for both plain entries and sub-batch inner records — sub-batch inner entries are views into the outer chunk string too, no longer copied into an intermediate sub-batch buffer first. `parseEntries()`/`parse()` (`ChunkEntry`-based) are unchanged; `Message::fromRawEntry()` is unchanged and still available for callers holding a standalone byte string. Measured on the `bench-batch` stream (200k × 1 KB messages, chunks up to ~6356 messages, `initialCredit=5000`): `Consumer::read()` peak memory 31 MB → 27 MB (≈13% less), `Consumer::readOne()` peak memory 25 MB → 17 MB (≈32% less); throughput unchanged within run-to-run noise. - **Performance: eliminated the two full-chunk copies on the consume path (#412, #484)** — a Deliver frame used to be copied twice before a single message could be read out of it: `DeliverResponseV1::fromStreamBuffer()` copied the whole chunk out of the frame via `ReadBuffer::getRemainingBytes()` (#412), and `OsirisChunkParser` then `substr()`-copied the declared data section out of that chunk again (#484). `ReadBuffer` gained a zero-copy window: `__construct(string $buffer, int $offset = 0, ?int $length = null)`, a new `getRemainingWindow(): array{0: string, 1: int, 2: int}` (the zero-copy counterpart of `getRemainingBytes()`), and `slice(int $offset, ?int $length = null): self` to derive nested windows — all scalar/array getters, `ensureAvailable()`, `getPosition()` (kept window-relative, so existing callers are unaffected) and bounds-check exceptions now operate against the window instead of the whole backing string. `DeliverResponseV1` now stores the whole frame buffer plus a `$chunkOffset`/`$chunkLength` window instead of a copied `$chunkBytes` string; `getChunkBytes(): string` is kept for backward compatibility (materialises the chunk lazily, only when actually called) and two zero-copy accessors were added: `getChunkView(): array{0: string, 1: int, 2: int}` and `getChunkBuffer(): ReadBuffer`. `OsirisChunkParser::parse()`/`parseEntries()`/`parseMessages()` gained optional `int $offset = 0, ?int $length = null` parameters so they can parse a chunk that lives inside a larger buffer without copying it out first (existing calls passing a plain chunk string are unchanged); internally, the entry-parsing loop now reads directly off the original chunk-carrying string with absolute cursor positions instead of `substr()`-ing the whole data section first. `Consumer`'s deliver callback uses `DeliverResponseV1::getChunkView()` end to end, so a Deliver frame is parsed straight out of the socket-read frame buffer with no full-chunk copy anywhere on the path. Measured on the `bench-batch` stream (200k × 1 KB messages, chunks up to ~6356 messages): `Consumer::read()`/`readOne()` peak memory dropped from 42.30 MB to 33.10 MB (≈22% less) consuming the whole stream; `OsirisChunkParser::parse()` on real ≥1 MB chunks (2–6.6 MB) is ≈25–33% faster (e.g. a 6.58 MB chunk: 2.95ms → 2.16ms average). - **Bug: Deliver frames were capped by the negotiated `frame_max`, causing a permanent "poison chunk" — consumer dies at the same offset on every restart** — the broker does not enforce `frame_max` on Deliver frames (key `0x0008`): a stream chunk is sent whole. A fast producer publishing several `sendBatch()` calls back-to-back without `waitForConfirms()` in between lets the broker's chunk writer coalesce them into a single on-disk chunk bigger than the negotiated `frame_max` (measured: 1.06 MB and 8.4 MB chunks from a burst of 1 KB messages against the default 1 MiB `frame_max`); because that chunk lives on the broker's disk, `readFrame()` threw `ConnectionException` ("Frame size N exceeds maximum allowed M") and closed the connection on every reconnect attempt at that offset, forever. `StreamConnection::readFrame()` now reads the frame's key before deciding which cap applies: Deliver frames are checked against a new, separate `maxDeliverFrameSize` (default 64MB via `setMaxDeliverFrameSize()`/`getMaxDeliverFrameSize()`/`StreamConnection::DEFAULT_MAX_DELIVER_FRAME_SIZE`), everything else keeps using `maxFrameSize` (8MB default) unchanged. `Connection::create()` gained a `?int $maxDeliverFrameSize = null` parameter. - **Performance: `Consumer::readOne()` was O(n) per call (`array_shift`)** — replaced with a head cursor (`bufferHead`) into the buffer array; elements are `unset()` in place instead of the whole array being shifted/reindexed, and the backing array is released (`buffer = []`) once fully drained. - **Bug: `Consumer` buffer could silently overshoot `maxBufferSize` by up to a whole chunk, and credit units were mixed (chunks vs. messages)** — the deliver callback now always accepts a full chunk into the buffer (never drops messages — at-least-once), but grants no new credit while `unreadCount >= maxBufferSize`; withheld credit (`pendingCredits`, chunk-granular) is sent once the buffer drains, capped so outstanding (in-flight) credit never exceeds `initialCredit`. `sendPendingCredits()` no longer compares a message-unit buffer count against a chunk-unit credit count. - **Security: `OsirisChunkParser` ignored `dataLength` — ~30x memory amplification from a single legal-sized chunk** — `dataLength` and `trailerLength` were read and discarded, so entry parsing was never bounded by the declared data section: a 7,864,608-byte chunk (under the 8 MB frame limit) produced ~1.97M `ChunkEntry` objects (~228 MB), blowing a typical 128–256 MB `memory_limit` with no exception. - **Security + Performance: `StreamConnection` no longer `bin2hex()`-logs every frame unconditionally** — `sendFrame()` and `readFrame()` previously called `bin2hex()` on every frame and logged the result at `debug` level, which (a) leaked the plaintext broker password and all message payloads into application logs whenever debug logging was enabled (the SASL `PLAIN` request body contains `\0username\0password` verbatim), and (b) paid the `bin2hex()` cost on every frame even with a `NullLogger` or any logger filtering out `debug` (~25% of a core and ~1 GB/s allocator churn for a 1 MB/frame consumer at 500 fps). - **Performance: `ReadBuffer` scalar getters avoid a `substr()` allocation per read** — `getUint16()`/`getUint32()`/`getUint64()`/`getInt16()`/`getInt32()`/`peekUint16()` now pass `unpack()` the buffer and offset directly instead of slicing a copy first; `getUint8()` uses `ord($buf[$pos])` instead of `unpack()`. Now: non-sentinel negative lengths throw `DeserializationException`, and array counts are bounded against the remaining buffer before the loop (≥ 2 bytes per string element, ≥ 1 per object). No wire-format change; valid input (including empty strings/bytes and zero-count arrays) still deserializes as before (#384)
- **`Producer::waitForConfirms()` — no longer blocks for the full timeout** — it called `StreamConnection::readLoop()` without `maxFrames`, and `readLoop()` never inspects `pendingConfirms`, so the loop kept running until the deadline expired even when the broker confirmed in milliseconds. Now passes `maxFrames: 1` (the pattern `Consumer::read()` already used), so the call returns as soon as the last confirm is dispatched. Every publish-then-wait workload previously ran at the timeout value instead of the broker's real confirm latency; the E2E suite dropped from ~302s to ~20s as a side effect. Upgrade note: `waitForConfirms()` no longer incidentally services the socket for the whole timeout, so an application that relied on it to dispatch unrelated server-push frames (deliveries, metadata updates) must call `readLoop()` itself (#385)
- **E2E test `ConsumerTest::testSubscribeFromTimestamp` — boundary derived from broker data** — the test sampled the client wall clock for its timestamp boundary, which could land in the same millisecond as the broker's "before" chunk; since `OffsetSpec::timestamp()` resolves to the first chunk with `chunkTs >= t` and delivers it in full, that leaked `before-*` messages into the filtered read. It now reads the stream back and derives the boundary from `Message::getTimestamp()` (the per-chunk timestamp the broker actually wrote), so it never compares a client clock to a broker clock (#385)
- `StreamConnection::readBytes()` — now sets `$this->connected = false` when a socket read error or EOF is detected (matching the pattern already used in `sendFrame()`); enables `isConnected()` to correctly report false after a server-initiated close or network failure (#151)
- E2E test handshake — `StreamStatsTest`, `ExchangeCommandVersionsTest`, and `PartitionsTest` now correctly use `TuneResponseV1` instead of `TuneRequestV1` when responding to the server's tune handshake; per protocol spec, client should respond with key 0x8014 (response bit set) not 0x0014 (#178)
- `StreamStatsResponseV1` — now uses `assertResponseCodeOk()` from `CommandTrait` instead of manual magic number check; provides consistent error messages with enum names and descriptions like all other response classes (#199)
- `Connection::close()` — now properly closes all outstanding producers and consumers before closing the connection; prevents server-side resource leaks and ensures consumer offsets are stored when autoCommit is enabled (#206)
- `PublishingError` — now implements `FromStreamBufferInterface` and changed return type from `self` to `?static` to match interface contract; enables polymorphic use with other VO classes (#201)
- `OpenRequest` → renamed to `OpenRequestV1` to follow naming convention; fixed interface declaration order to match other request classes (#195)
- `StreamConnection::unregisterPublisher()` — added missing method to clean up publisher callbacks when `Producer::close()` is called; fixes resource leak where publisher callbacks accumulated in memory (#202)
- `AmqpDecoder::readUint64()` — replaced bit-shifting implementation with `unpack('J')` to fix integer overflow on 32-bit PHP and negative value issues on 64-bit PHP when reading large uint64 values (#220)
