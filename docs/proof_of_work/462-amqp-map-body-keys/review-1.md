## 1. Correctness of the fix

### Before / after

```php
// before
if (is_array($rawBody)) {
    $body = array_values($rawBody);
} elseif ($rawBody === null || is_scalar($rawBody)) {
    $body = $rawBody;
} else {
    $body = null;
}

// after
if (is_array($rawBody) || $rawBody === null || is_scalar($rawBody)) {
    $body = $rawBody;
} else {
    $body = null;
}
```

The merged condition is **exactly** `old-branch-1 || old-branch-2`: `is_array()` and
`is_scalar()` are mutually exclusive, and `null` is not scalar, so no value can fall
into a different arm than before. The only behavioural delta is that an array body is
no longer passed through `array_values()` — which is the point of the fix. Objects and
resources still map to `null` exactly as before. **Verified logically and by inspection
of `Message.php:225-233`.**

### Map keys preserved / lists still sequential

`AmqpDecoder` builds maps and lists differently:

- `readMap8` / `readMap32` (`src/Client/AmqpDecoder.php:742-743`, `:841-842`) write
  `$map[$mapKey] = $value`, so the result can carry `string|int` keys.
- `readList8` / `readList32` / `readArray8` / `readArray32` (`:675-681`, `:705-711`,
  `:771-777`, `:799-805`) all use `$list[] = ...`, which is already a `list`.

`array_values()` was a no-op on the lists and destructive on the maps, so "keep as-is"
preserves maps and changes nothing for lists. Confirmed empirically (scratch script,
`/private/var/.../scratch462.php`, outside the repo):

```
map {"a":1,"b":2}     -> array("a"=>1,"b"=>2)   (pre-fix array_values() -> [0=>1,1=>2])
int maps {0:'x',2:'y'} -> array(0=>'x',2=>'y') (non-sequential int keys preserved)
list [1,2,3]           -> array(0=>1,1=>2,2=>3)
raw section body       -> array('a'=>1,'b'=>2)
```

### Was `array_values()` ever load-bearing?

Searched every consumer of the body:

- `getBody()` is called in `src/` **only** at its own definition (`Message.php:267`).
  There is no `MessageInterface`, so no other signature to keep in sync.
- `TypeCast::toArray()` calls `array_values()` (`src/Util/TypeCast.php:103`) but is
  never used anywhere under `src/Client/` — it is a response-parsing helper, not on the
  message-body path.
- Every `getBody()` use in `tests/E2E/` compares against a string (or nested lists,
  e.g. `[[[[null]]]]`), never a keyed map that relied on re-indexing.
- `array_values()` calls in `Connection.php:302`, `Consumer.php:517`,
  `Routing/KeyRoutingStrategy.php:34` operate on genuine collections, unrelated and
  untouched.

**Conclusion: no in-repo caller relied on the old re-indexing.** The pre-fix
constructor path (`new Message(body: ['a'=>1])`) already preserved keys; only the lazy
decode path re-indexed, so the fix also removes an internal inconsistency.

- `Message::__construct()` `@param` and `getBody()` `@return` widened to
  `array<int|string, mixed>|string|int|float|bool|null` (`Message.php:17`, `:266`).
  This matches `readMap8/32`'s declared `@return array<string|int, mixed>` and is a

  `array<int, mixed>` at lines 14, 32, 59 and 204. Because that page is generated by
  hand from the source PHPDoc, it no longer matches the public contract. (low, F1)

## 3. Test quality and bug reproduction

Fixtures are hand-built AMQP. I recomputed the byte accounting and ran both tests
through the real decoder (hex emitted for the map fixture):

```
map:  00 53 77  c1 0b 04  a1 01 61 52 01  a1 01 62 52 02
      AmqpValue  map8 size=11 count=4  "a" 1     "b" 2
      size 11 = count byte (1) + 10 content bytes  ✔
list: 00 53 77  c0 07 03  52 01 52 02 52 03
      AmqpValue  list8 size=7 count=3  [1,2,3]
      size 7 = count byte (1) + 6 content bytes      ✔
```

- `testDecodeAmqpValueWithMapBodyPreservesKeys` exercises the **lazy** path that
  actually contained the bug (`AmqpMessageDecoder::decode()` → `Message::fromRawEntry()`
  → `ensureDecoded()` → `applyDecodedSections()`), not the fast Data path. It **would
  fail pre-fix**: `array_values(['a'=>1,'b'=>2]) === [1,2]`, so
  `assertSame(['a'=>1,'b'=>2], ...)` would fail. Confirmed by reproducing the pre-fix
  `array_values()` result. ✔ genuine regression test.
- `testDecodeAmqpValueWithListBodyReturnsSequentialList` is a guard, not a reproducer
  (passes before and after). Its doc comment says exactly that. Reasonable.
- The added `buildAmqpValueSection()` helper mirrors the sibling helper in
  `AmqpDecoderMessageTest` and fits the file's existing `build*Section()` family.

Optional (nit, F6): neither test covers a map with **non-sequential integer** keys
(e.g. `{0:'x', 2:'y'}`), which is the one shape where "keep as-is" is observably
different from "reindex" beyond string-key loss. The string-key test already fails
pre-fix, so this is a nice-to-have, not a gap in coverage of the bug.
